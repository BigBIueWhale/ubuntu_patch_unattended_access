Unattended Remote Access on Ubuntu 24.04 Wayland

Why the “Portal” Prompt Appears, How GNOME & RustDesk Handle It, and Why It Sometimes “Breaks Overnight”

Audience: Readers with no prior context about Wayland, XDG Portals, GNOME, or RustDesk specifics.

0) Your Goal & Observed Symptoms (as established from your setup)

  • Goal: Headless/unattended, reliable remote control of an Ubuntu 24.04 LTS machine running Wayland (GNOME), using tools like RustDesk/TeamViewer — without a local user having to approve a dialog pop-up each time.
  • Your environment: Ubuntu 24.04 GNOME Wayland; Intel iGPU driving a port; you use an EDID/HDMI/DP “display stub” so the compositor believes a monitor is present; you prefer Wayland because GNOME/Mutter keeps VRAM usage low vs Xorg.
  • The prompt: When a Wayland “remote desktop” session is requested, a “Portal — Remote Desktop” dialog appears with a toggle Allow Remote Interaction, and “Cancel/Share” buttons. With multiple monitors, you must choose one. Unattended, this blocks you.
  • What starts working (temporarily): After you manually approve once, subsequent connections often succeed silently (no prompt) — until the display topology changes (different EDID, added/removed displays) or the persisted authorization chain breaks. You observed a case where it “just stopped overnight.”

Executive summary of the root causes:

  1. On GNOME Wayland, user consent is enforced via the XDG Desktop Portal. The GNOME backend presents that dialog by design.
  2. The portal offers persistence using a single-use restore_token. After each successful start, a new token must be stored for the next unattended session. If the application misses writing back the new token once, the chain is broken and unattended access fails until someone clicks “Share” again.
  3. Changing monitors / EDIDs can invalidate the stored session entirely, forcing a new approval even if tokens were rotated correctly.

1) Where the Prompt Comes From: GNOME’s XDG Desktop Portal (Wayland)

Wayland restricts screen capture & input injection. Applications must go through the Cross-Desktop “XDG Portal.” GNOME’s backend (xdg-desktop-portal-gnome) implements the actual dialog you see.

1.1 The Dialog and its “Allow Remote Interaction” Switch (GNOME code)

  • GNOME portal backend (C): remotedesktopdialog.c (lines 14–27) — constructs and controls dialog state.
  • UI description (GTK/libadwaita): remotedesktopdialog.ui — defines widgets including the Allow Remote Interaction switch.

Two details in the GNOME backend are crucial:

  1. Input devices disabled unless the switch is active. The device mask (keyboard/mouse/touch) that remote apps receive is empty unless the user turns on Allow Remote Interaction. This is handled inside the dialog logic. (See remotedesktopdialog.c.)
  2. “Share” button inactive until user selects a monitor and/or enables the switch. The dialog disables “Share” until a shareable target is chosen. Again handled in the same C file and backed by the .ui file’s switch widget.

Net effect: Absent a persisted authorization that can be restored, a local user must interact with the dialog to grant control.

2) The Portal’s Persistence Model (Why approval seems to “stick” — and why it stops)

The Wayland Remote Desktop portal is documented at:

  • org.freedesktop.portal.RemoteDesktop

Key points from the spec (version 2):

persist_mode — “How this session should persist. 0: no persist, 1: persist while the app runs, 2: persist until explicitly revoked.”

restore_token — “The restore token is invalidated after using it once. To restore the same session again, use the new restore token sent in response to starting this session.”

So the persistence mechanism is a chain of single-use tokens:

  1. App calls SelectDevices with persist_mode=2 and (optionally) a restore_token from last time.
  2. App calls Start. If restoration succeeds, the portal returns a new restore_token to use next time.
  3. The app must store this new token immediately. If it fails to do so even once, next unattended connect will try the old (already consumed) token and fail.

This is why your setup sometimes “just dies overnight.” There is no arbitrary clock-based “expiry” in your app. The token is single-use: if it wasn’t rotated, your next unattended run is dead until someone approves again.

3) How RustDesk Uses Wayland Portals (Where the logic lives)

RustDesk’s Wayland portal glue code lives in:

  • File: libs/scrap/src/wayland/pipewire.rs

3.1 Which portal is called? Screencast vs Remote Desktop

RustDesk decides based on whether the process is running as the server:

// create_session branching
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L592-L600
if is_server_running() {
    path = screencast_portal::create_session(&portal, args)?;
} else {
    path = remote_desktop_portal::create_session(&portal, args)?;
}

// start branching
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L818-L823
if is_server_running() {
    screencast_portal::start(&portal, &session, handle)?;
} else {
    remote_desktop_portal::start(&portal, &session, handle)?;
}

The detection function:

// is_server_running
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L927-L953
fn is_server_running() -> bool {
    let app_name = config::APP_NAME.read().unwrap().clone().to_lowercase();
    let output = Command::new(CMD_SH.as_str()).arg("-c")
        .arg(&format!("ps aux | grep {}", app_name)).output();
    let output_str = String::from_utf8_lossy(&output.stdout);
    output_str.contains(&format!("{} --server", app_name))
}

Interpretation: when RustDesk runs as a server on your Ubuntu host, it goes through the Screencast portal for video; when it acts as the remote client, it uses the Remote Desktop portal. Both paths can request persistence; the crucial part is how tokens are handled after a successful start.

4) Where RustDesk Already Handles Persistence (Screencast path)

On the Screencast (server) branch, RustDesk passes persist_mode=2 and an existing token (if stored), then stores the new token it receives. The relevant snippets are:

// Passing persist_mode=2 and restore_token before SelectSources
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L692-L699
if is_support_restore_token {
    let restore_token = config::LocalConfig::get_option(RESTORE_TOKEN_CONF_KEY);
    if !restore_token.is_empty() {
        args.insert(RESTORE_TOKEN.to_string(), Variant(Box::new(restore_token)));
    }
    args.insert("persist_mode".to_string(), Variant(Box::new(2u32)));
}

// Saving the NEW token on Start response (guarded by is_server_running)
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L258-L266
if is_server_running() {
    if is_support_restore_token {
        if let Some(restore_token) = r.results.get(RESTORE_TOKEN) {
            if let Some(restore_token) = restore_token.as_str() {
                config::LocalConfig::set_option(
                    RESTORE_TOKEN_CONF_KEY.to_owned(),
                    restore_token.to_owned(),
                );
            }
        }
    }
}

Important nuance: the “save” lives inside a guard that checks is_server_running(). If for any reason the callback runs when that check is false, the new token won’t be stored — and the next unattended session will try to reuse a stale token.

5) Where Persistence Is Not Implemented (Remote-Desktop branch)

In the Remote-Desktop (client) branch, RustDesk currently:

  • Calls SelectDevices but does not add persist_mode nor a restore_token argument there.
  • Calls Start but does not store any returned restore_token for next time.

See argument construction for SelectDevices (no persist args):

// Remote-Desktop select_devices args (no persist or restore_token)
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L725-L747
args.insert("handle_token".to_string(), Variant(Box::new("u2".to_string())));
args.insert("types".to_string(), Variant(Box::new(7u32))); // all device types
let path = portal.select_devices(ses.clone(), args)?;

And the Start call (no token handling on return):

// Remote-Desktop Start
// https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/src/wayland/pipewire.rs#L818-L823
remote_desktop_portal::start(&portal, &session, handle)?;

Implication: even though your machine is in server mode (so you’re on Screencast for video), any path that happens to rely on Remote-Desktop token restoration will not be rotating a token in this branch — and the write-back is also guarded in the Start callback. A single missed rotate leaves you with a dead, single-use token in ~/.config/rustdesk/RustDesk_local.toml, which matches the “it died overnight” symptom.

6) Not a Time Expiry: A Setup Timeout vs Token Invalidity

There is a ~3-minute wait loop for user interaction with the portal dialog; if nobody clicks share within that window, the attempt is aborted. This is not a lifetime expiry — it’s just a setup timeout. (See comments around the waiting code in the same file.)

  • Reference: pipewire.rs:188–194

The “overnight stop” you hit is explained by single-use tokens + missed rotation, not by any clock-based expiration inside RustDesk.

7) Display Topology Changes Force Re-approval

Even with perfect token rotation, the portal spec states that restoring will be ignored if the stored session no longer matches reality (e.g., the selected monitor no longer exists):

“If the stored session cannot be restored, this value is ignored and the user will be prompted normally. This may happen when, for example, the session contains a monitor or a window that is not available anymore, or when the stored permissions are withdrawn.” — portal docs

Your EDID/HDMI/DP emulator makes topology stable, but if the dongle is swapped, unplugged, or the compositor’s view of displays changes, the portal can cancel restoration and re-prompt.

9) The “If Only…” (what would need to be different for truly reliable, no-prompt, headless use)

Given the current upstream code and Wayland/GNOME design, unattended remote control would be truly reliable if only the following were different:

  1. If only GNOME’s Remote Desktop portal offered a system-wide admin pre-authorization policy (e.g., “always allow for app X on this machine”), you wouldn’t need per-session, single-use tokens at all. (KDE Plasma has introduced portal pre-authorization; GNOME has not exposed an equivalent admin knob.)
  2. If only the portal’s restore_token were multi-use (or the persisted grant worked without token rotation). The single-use design is what requires the app to save a fresh token every time — any missed write bricks unattended access.
  3. If only application code always rotated tokens in every path (server and remote-desktop branches, and regardless of transient role detection). With guaranteed rotation, a single successful start would never leave you stranded on the next attempt.
  4. If only display topology changes didn’t invalidate restoration. Restoration failing when monitors change is intentional for safety; but for headless servers with fixed EDID stubs, an admin override (“always share Display 0”) would eliminate prompts after reboots or cabling stories.

As things stand, GNOME’s security model (consent per session, single-use tokens, topology checks) plus RustDesk’s current token-handling asymmetry can combine to produce exactly what you’ve seen: it works after one approval, then silently stops later unless everything aligns perfectly.

12) Closing

This report documented the complete chain, from GNOME’s enforced consent model and UI, to the XDG portal’s single-use restore tokens, to RustDesk’s current Wayland code paths. Your experience (works once, then dies unattended until a new approval) follows directly from that chain: single-use tokens require perfect rotation on every successful start, and anything that breaks that rotation (or changes the display set) forces a new approval.

As you put it: “If only it didn’t have X, Y, Z, everything would work.” Concretely, “X, Y, Z” are: (X) no admin pre-authorization in GNOME’s portal, (Y) single-use restore tokens that demand constant rotation, (Z) restoration invalidated by display changes. With those constraints removed, unattended Wayland remote control would be as simple as you expect from a headless server.
